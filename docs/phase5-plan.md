# Phase 5 設計・実装計画

作成日：2026-10-17 JST。基点：`d7c2047`（Phase 4.5）。本書は設計であり、未実装の機能を実装済みとして扱わない。

## 1. 今回の範囲と初期状態

既存のSupabase継続口座・口座作成日時・資金・判断・注文・API使用履歴を維持する。破壊的migration、初期資金の再付与、使用枠のリセットは行わない。

初期状態はスケジュールなし、継続口座の注文登録なし。最初は `test-phase5-*` の明示的なテスト口座だけを対象に、手動実行で確認する。設計報告の次に、以下の順序で実装する。現在のWorkflow、SQL、運用設定を本書の作成によって変更しない。

## 3. 実行単位と処理順

初期のAI判断頻度は各市場1営業日1回。約定処理は市場稼働中の確定足更新後に行い、AIを再呼出ししない。頻度変更は使用枠・データ遅延の検証後に別設定とする。

論理キーは `(account_scope, market, session_date, job_kind, slot)`。GitHub run IDは試行の識別子として別保存する。設定・モデル・プロンプト・コミットのハッシュを実行に固定するが、ハッシュ変更で同じスロットの新注文を許可しない。

通常の処理順：

1. モード、対象口座、運用停止フラグ、Supabase接続、migration整合性を確認。継続口座が見つからなければ失敗し、自動再作成しない。
2. 市場カレンダーで予定スロット・許容遅延を判定し、DBでclaim。休場は理由付きSKIPPED、対象外口座は拒否。
3. 非公開の既存データとmanifestを読み、保有銘柄・未約定注文・候補銘柄の不足履歴と重複期間を取得。
4. OHLCV・時刻・市場整合性、取得範囲、FX、株式分割/配当情報を検証。合格したデータセットを確定する。
5. 既存注文を後続の確定足で約定処理。約定・残高・台帳を原子的に保存し、必要なら評価を更新する。
6. 判断スロットのときだけ最新の口座・未約定注文・価格/FXを再読込し、API枠予約→Gemini→構造検証→リスク判定→仮想注文登録。
7. 同じ時点の入力で資産評価・実行要約を保存する。新規注文はこの実行内で約定させず、後続の取得処理へ渡す。
8. 公開可能なDTOのみ別段階で更新。公開失敗で売買・AIを再実行しない。

各段階は独立したcheckpointを持つ。全体を1つの長時間DBトランザクションにせず、ネットワーク通信中にDBロックを保持しない。途中で約定だけ成功し、AIが失敗した場合、正しい約定を巻き戻さず実行をPARTIALとする。

## 4. 二重実行防止・再開

GitHubのaccount単位concurrencyに加え、DBの一意キー・短い原子的claim・期限付きlease・単調増加fencing tokenを使う。JP/USも共有残高を変更するため口座単位でwriterを直列化し、既存manual経路からも停止状態と排他を確認する。

DB時刻でleaseを発行/更新する。期限切れ後に旧runnerが復帰しても、古いtokenで注文・約定・実行状態をcommitできない。leaseの失効はAPIの再送許可を意味しない。全mutation RPCに適用し、全体CASによる競合検出も維持する。

注文・約定・仮想両替は論理キーから決定的IDを作り、再実行で同じイベントを二重計上しない。API通信直前に永続予約と外部呼出し開始状態を保存する。通信結果・DB commit応答が不明なら `NEEDS_REVIEW` とし、同一キーをDBで照合する。確実な結果が判明する前に別IDでやり直さない。

GeminiとDBを跨ぐ厳密なexactly-onceは保証しない。安全側として、応答保存前の中断は使用枠を残したまま自動再送せず、判断/登録を停止する。履歴を消してclaimや枠を取り直す復旧はしない。

## 5. 株価・為替と永続データ

非公開のSupabase Storageを第一候補に、世代付きParquetとmanifestを保管する。採用前に既存プランの容量・転送量・提供元の内部保存条件を確認する。条件が満たせなければこの段階で停止し、Git管理や公開artifactを永続データベースの代わりにしない。

objectを不変キーでupload→検証済みSHA-256とデータ範囲をDBへCAS commit。readerはcommit済みmanifestだけを参照する。upload途中/commit失敗時の孤立objectは別途回収し、既存の正常世代を上書きしない。Actions cacheは任意の高速化だけに使用する。

watermarkは銘柄・市場・足種・provider・調整方針ごとに管理する。直近重複期間を再取得し、全行検証後にupsertする。初期データや長期停止後には必要な指標期間をbackfillし、取得元の時間足提供期間を超えた欠落を別の足や0で埋めない。訂正内容・原本ハッシュ・観測時刻を監査する。

FXProviderはUSD/JPYのレート時刻、観測時刻、出所、通貨方向を保存し、リクエスト時刻を価格時刻として使わない。Yahoo等の利用条件・実取得で候補を選定する。基準の鮮度上限は既存の3,600秒を維持する。未確定足・将来値・非数値・欠損・逆通貨の無検証な代用は拒否する。確定1時間足では常時鮮度条件を満たせない場合があるため、より短い足/時刻付き観測を別契約で検証し、閾値を緩めて通さない。

USD残高/米株保有・米株BUYがある場合は新鮮なFXを要求する。JPYだけの口座で必要がなければ不要。USD不足を暗黙に補充せず、テスト口座では明示した仮想両替方針・上限・コスト・決定的ID・台帳整合を先に検証する。継続口座の仮想両替も初期状態では禁止する。

## 6. カレンダーと注文時刻

内部はUTC、JP営業日はAsia/Tokyo、US営業日はAmerica/New_Yorkのセッション日で識別する。JP昼休み、国内祝日、US祝日、短縮取引、DST移行前後をカレンダーから計算する。UTC日付をそのまま米国営業日に使わない。

将来のscheduleは広めのUTC候補時刻から起動し、アプリが実セッションとslotで実行可否を決定する。現段階ではYAMLに `schedule` 自体を追加しない。GitHubは遅延・欠落があり、正確な時刻の起動を前提にしない：[公式仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

判断は当該セッションの必要な足がすべて確定し、取得猶予を経てから実行する。既存実装は最終の短い時間足でも名目1時間の確定を待つため、単純な「引け直後」固定にはしない。許容遅延は初期案30分とし、データ提供遅延の実測で確定する。期限超過した判断はSKIPPEDとし、過去の判断時刻を偽って発注しない。

約定には注文時刻より後に開始した最初の適格な確定足を使う。同じ判断足・過去に取得済みの足・未確定足では約定しない。過去足が欠落している場合は都合のよい後続足を選ばず停止する。古い注文の有効期限、休日を跨ぐ扱い、再開時の失効は明示した規則で判定する。

休日の評価は最終の検証済み評価とその基準時刻を保持し、新しい同時点の評価として捏造しない。片方の市場が休場しクロス市場保有の鮮度条件を満たさない場合、新規判断/発注を止める。市場横断の古い価格を許す評価方針への変更は別途設計・検証を要する。

## 7. 分割・配当

価格と独立したCorporateActionProvider/観測記録を追加し、分割率、配当額/通貨、権利落日、分かる場合の支払日、観測時刻、訂正世代を保存する。取得成功と「イベントなし」を区別し、取得失敗を空一覧として正常扱いしない。

価格不連続との二系統で検出する。権利落日だけでは入金日・受取数量・税額が確定しないため、Phase 5初期は保有/注文銘柄の対象イベントを検出すると口座の新規注文・該当約定・信頼できない評価を停止する。配当を勝手に現金へ入れたり、分割時に数量/原価/注文を無監査に調整しない。過去イベントを後から発見した場合も対象期間の評価を要確認にする。

口数調整・配当入金の完全自動会計は、この検出/停止から独立した追加承認対象とする。正確な台帳処理が確認できるまで、保有イベント検出時の継続運用は再開不可。異常な値動きをすべて分割と決めつけない。

## 8. 状態・異常検知・停止

実行状態は `CLAIMED / FETCHED / VALIDATED / EXECUTED / DECIDED / REGISTERED / VALUED / SUCCEEDED` をcheckpointとして持ち、終端は `SKIPPED / PARTIAL / FAILED / NEEDS_REVIEW` を区別する。AIのHOLD、API失敗、取得失敗を同じ「成功」にまとめない。

異常イベントは実行欠落、重複claim、期限超過、データ/FX鮮度、不連続、企業行動、API 429/503、使用枠枯渇、DB/Storage障害、台帳差異、公開更新失敗を分類する。account/market/symbol、stage、発生/検出時刻、関連ID、秘匿済みerror_codeを残す。

| 障害 | 安全動作 |
| --- | --- |
| Supabase停止・停止フラグ確認不能 | AI送信・注文・約定・両替を行わない。SQLite/別口座へのfallbackなし |
| API予約の応答不明 | Geminiへ送信しない。復旧後に予約IDで照合。枠は返却しない |
| Gemini 429/503/timeout | 当該slotのAIは停止。初期は1通信、SDK/アプリretry 0、有料fallbackなし |
| Gemini成功後、結果保存不能 | 新規注文登録禁止、結果不明として要確認。自動再送なし |
| 注文/約定commit応答不明 | 決定的IDで照合するまで後続mutation停止 |
| データ・FX・企業行動異常 | 影響範囲に応じ注文/約定/評価を停止。残高を都合よく補正しない |
| 公開だけ失敗 | 既存公開値と更新時刻を維持、売買再実行なし |

共有口座状態の整合性が疑われる異常は口座全体を停止する。小さな銘柄別取得失敗は正常な保存結果を保持するが、必要な保有/注文データが欠けるならその口座の判断・登録を止める。安全停止時も監査・読取・照合を可能にし、再開は理由と操作者を記録する。

DB障害中はDBへ異常を記録できないため、Secret・原株価・AI原文を含まない最小のrunnerログ/Job Summaryに残す。workflow欠落は当のworkflow自身では検知できないので、独立healthcheckで予定スロットとDB履歴を照合する。GitHub全体の停止を同じActionsだけでは検知できない制約を明示し、外部監視が必要なら後で別途設定する。外部メッセージ送信は今回行わない。

## 9. API枠

既存の全口座共通・UTC暦日/月のSupabase予約方式を維持する。テスト口座の実Gemini通信も同じ枠を消費し、テスト終了・失敗・口座削除で戻さない。既存初期値は日5・月100・1実行1通信・retry 0であり、提供元の実際の契約枠と別の内部上限である。

JP/US各日1判断に制限し、最初の統合テストはmock。実Gemini試験の直前に当日/月の残枠と予約を確認し、1市場1通信ずつ段階実施する。月100の内部上限でも休業日・試験・失敗分を含めて実算し、枠を拡張して試験を通さない。

| --- | --- | --- |

## 11. DB・実装分割

追加候補はprivate schema内の `operation_runs / operation_steps / operation_controls / data_manifests / data_watermarks / fx_observations / corporate_action_observations / operational_alerts` と、claim/lease更新・fenced commit・停止/再開のRPC。既存API予約台帳・会計台帳は再利用し、別の使用枠を作らない。実装時に重複を避けるためテーブル分割は最小限に調整する。

既存Sessionで許可するrecord kind、RPC権限、RLS、CASとの整合を更新する。既存口座への加算/削除SQLは含めず、追加前後で口座JSON・台帳件数・判断件数・API予約件数/IDを比較する。テストデータは別scope、migration試験は別DB。実DB適用前に非公開バックアップと復元検証を行う。

| 実装段階 | 主な成果物 | 合格条件 |
| --- | --- | --- |
| P5-1 | 設定、session/slot、状態契約、追加SQL、排他・停止制御 | scheduleなし、継続口座mutation拒否、既存データ維持 |
| P5-2 | 非公開の差分データ/manifest、FX、企業行動検出 | 再実行・中断・欠落・古いFX・イベント検出が安全側に動く |
| P5-3 | test限定runner、mock判断→注文→後続約定→評価 | 複数の独立した起動を跨いだ台帳整合、二重計上なし |
| P5-4 | 手動Workflow、履歴/healthcheck/reconcile、障害注入 | DB停止・通信結果不明・lease期限切れ・同時起動の安全停止 |
| P5-5 | 制限した実データ/実Gemini手動試験 | 実市場時刻・実FX・共有枠維持を確認。503時は停止 |
| P5-6 | 稼働判定報告、開始用変更案 | 許可前はscheduleも継続口座注文も無効のまま |

## 12. 追加テスト

既存Python318件・Web13件を回帰基準とする。これはPhase 4.5の確認済み件数であり、本設計作成時に再実行したと主張しない。追加件数は実装後に実測する。

- カレンダー：JP祝日/昼休み、US祝日/短縮日、DST開始/終了、UTC日付跨ぎ、最終時間足の確定待ち、遅延・slot欠落。
- 排他：同じslot同時実行、JP/US同一口座、manualとの競合、期限切れlease、古いrunnerのcommit、設定変更/再実行でも新注文不可。
- 中断復旧：各checkpoint前後で強制終了、予約応答不明、Gemini成功直後停止、commit成功後の応答喪失、公開失敗。再実行で残高・注文・約定・使用枠が増殖しない。
- 株価：使い捨てrunner再起動、初回/差分/重複/訂正、部分失敗、欠落期間、未確定足、manifest競合、破損/不完全upload、正常旧世代の保持。
- FX：境界3,600秒/超過、未来時刻、観測時刻による偽装防止、通貨方向、欠損、取得失敗、USD不足、二重両替なし、JPYのみなら不要。
- 分割/配当：既知split・併合・配当、遅れて発見、訂正、データなし/通信失敗の区別、不連続のみのケース、関連注文/評価の停止、無断の台帳変更なし。
- API枠：UTC日/月跨ぎ、全口座競合、枠枯渇、429/503/timeout、失敗予約維持、実試験とmockの分離、無制限retryなし。
- 会計：注文登録と後続約定が別起動、同足/過去足約定禁止、最初の適格足の欠落、失効、部分成功、現金/数量/原価/損益照合、資産評価の不足値を0にしない。
- Supabase：停止/遅延/認証エラー、Storage単独障害、CAS競合、fencingと既存経路の互換、RLS、既存口座/履歴の非破壊migration。
- 公開：異常コードと更新時刻だけの最小表示、Secret/原データ/内部IDの非公開、未許諾NAVおよび派生値の非公開、公開失敗で売買を再実行しない。
- Workflow：scheduleキーなし、test限定、dry-run初期値、Secretの分離、コマンド注入/不正input、失敗時の非0終了、外部ネットワーク不要のCI。

実市場統合はJP/US各1往復のtest売買を最低条件とし、登録・後続足取得・約定を別の手動起動で検証する。mock戦略は売買を意図的に発生させるが、実GeminiのHOLDを失敗とは扱わず、売買するまで何度もAPIを呼ばない。

## 13. 段階的な稼働開始条件

3. **隔離口座・手動Gemini**：内部/提供元の枠確認後に限定実施。成功/失敗を監査し、結果不明の再送なし。
4. **隔離口座・継続観測**：少なくともJP/US各5営業日の手動実行と日次照合。祝日/DST/分割/停止は合成試験で補い、実日待ちで未検証を隠さない。
5. **稼働判定**：実行遅延・欠落、必要なデータ提供/保存条件、容量・無料枠、復旧手順、停止解除の実証を報告。未解決なら起動しない。
6. **明示的な開始許可後だけ**：まず隔離口座の定期実行、安定確認後に継続口座の手動dry-run、さらに別途許可された場合のみ継続口座の仮想注文へ進む。schedule開始と継続口座注文開始は別の許可/設定として扱う。
